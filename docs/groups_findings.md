## Blockers

1. **Blocker · [§7.5 leaderboard RPC](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:328) · (a) definitely broken** — **Defect:** The RPC accepts arbitrary `p_start` and `p_end`, contradicting the fixed 7/30-day product rule and the claim that individual set dates never leak. **Failure:** A member calls it once per day with `p_start = p_end = '2026-08-15'` and learns exactly who trained which discipline on August 15. They can enumerate an entire year with 365 cheap calls. **Fix:** Accept only a period enum, not dates. Compute the current 7/30-day range inside Postgres. To preserve viewer-local dates, accept a validated IANA timezone and compute “today” server-side. Never accept an arbitrary historical end date.

2. **Blocker · [§6 reaper and EC-5/EC-12](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:233) · (a) definitely broken** — **Defect:** The empty-group check is not serialized. The recursion explanation is sound, but the concurrency claim is not. **Failure:** Group has members A and B. A and B delete their separate membership rows concurrently. Each trigger sees the other membership because the other deletion is uncommitted, so neither deletes the group. Both transactions commit, leaving a permanent zero-member group. Separately, `join_group` can observe the group, then lose a race to the last leave and raise an unmapped `23503` FK violation rather than `P0002`. PostgreSQL’s default Read Committed isolation does not make these multi-statement decisions atomic. [PostgreSQL documents the snapshot behavior here.](https://www.postgresql.org/docs/current/transaction-iso.html) **Fix:** Use one per-group transaction lock shared by join, leave, and the cleanup trigger—such as a transaction-scoped advisory lock—then recheck existence/membership after acquiring it. Add real concurrent database tests, including account-deletion cascades.

3. **Blocker · [§5 and §7 privileges/definers](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:159) · (b) suspicious, must verify against the live ACLs** — **Defect:** The migration specifies RLS but no explicit table or function grants/revokes. It also puts every definer function in exposed `public`, grants depend on ambient defaults, and uses `search_path = public, extensions`. **Failure:** On projects using Supabase’s new opt-in exposure defaults, the client receives `42501 permission denied` before RLS or the function runs. Under legacy defaults, new definer functions may instead be executable by `PUBLIC`/`anon`, making every authentication guard load-bearing. Supabase began rolling out explicit grants in May 2026 and plans enforcement for existing projects on October 30, 2026. [The change explicitly requires migrations to add grants.](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically) **Fix:** In the same transaction:

   - Revoke all table privileges by default; grant only the precise direct operations needed for `user_blocks`.
   - Revoke function execution from `PUBLIC` and `anon`; grant each RPC signature to `authenticated`.
   - Prefer private definer helpers behind a narrow exposed wrapper.
   - Use `SET search_path = ''` and qualify every relation. This is current [Supabase function guidance](https://supabase.com/docs/guides/database/functions).
   - Verify `has_schema_privilege('authenticated','public','CREATE')` and every effective table/function ACL in production.

4. **Blocker · [§10.2 moderation](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:601) · (a) definitely noncompliant as designed** — **Defect:** Report-plus-one-way-hiding is not enough for public UGC.

   **Failure:**

   - There is no method for filtering objectionable group text before publication.
   - Offensive `profiles.full_name` content cannot be reported at all.
   - A block only removes B from A’s board; B continues seeing A’s name and training volume, and groups created by B remain visible to A.
   - Reports produce no notification or response workflow, so “reviewed in the dashboard” does not ensure a timely response.
   - `group_reports.group_id ON DELETE CASCADE` destroys the report when the offender leaves as the last member. The abusive group and all moderation evidence disappear together.

   Apple requires filtering, reporting with timely responses, blocking abusive users, and published contact information. [Guideline 1.2](https://developer.apple.com/app-store/review/guidelines/) is explicit. Google additionally requires ongoing moderation, terms acceptance before creating UGC, and in-app reporting of users and content. [Google Play’s UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937?hl=en-GB) is likewise explicit. **Fix:** Add server-side filtering, report-group and report-user flows, retained report snapshots, alerting plus a response/takedown runbook, and block semantics that suppress visibility in both directions and cover directory content. Keep moderation records after group deletion.

## Serious findings

5. **Serious · [§5 groups policy and §7.5 return shape](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:167) · (a) definitely broken** — **Defect:** Cross-user stable identifiers escape the promised aggregate-only envelope. **Failure:** If `authenticated` has table `SELECT`, `/rest/v1/groups?select=*` returns `created_by` for every group because RLS is row-level, not column-level. The leaderboard also returns the underlying `auth.users` UUID as `member_id`, allowing callers to correlate the same person across groups and name changes. **Fix:** Do not grant direct `groups` access; expose only `list_groups`. Do not return auth user IDs. Add a random group-membership identifier and let `block_group_member(group_id, membership_id)` resolve the user internally.

6. **Serious · [existing profile schema](/C:/dev/iSkiLog/tests/e2e/db/schema.sql:3) and [ProfileSettings](/C:/dev/iSkiLog/src/pages/ProfileSettings.tsx:66) · (a) definitely broken** — **Defect:** `profiles.full_name` becomes public UGC, but it has no database length or content constraint and remains directly writable. **Failure:** A user stores a very large or abusive name, joins a group, and every leaderboard response carries it. This can inflate responses and gives the app unreportable offensive content. **Fix:** Add a database maximum, normalize control whitespace, clean existing rows before adding the constraint, and include profile-name reporting/moderation.

7. **Serious · [D13 plus list_groups](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:42) · (a) definitely dangerous** — **Defect:** Anyone can create unlimited groups while every client downloads and aggregates the entire directory. **Failure:** One account creates tens of thousands of uniquely named groups and remains a member. Every directory load becomes a large table scan, aggregate, network response, and mobile render. Nothing in RLS or the RPC stops it. **Fix:** Add server-side creation quotas and time-based throttling now. A reasonable active-group quota does not contradict “anyone may create.” Retaining unlimited, unpaginated results is unsafe once creation is unrestricted.

8. **Serious · [§7 RPCs and §13 tests](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:270) · (a) definitely incomplete** — **Defect:** Six RPC bodies are prose, and the `list_groups` fragment is not executable SQL. Consequently, output-variable ambiguity, exception scoping, auth checks, function volatility, and grants cannot actually be audited. The test plan drives UI behavior but does not attack the database boundary. **Failure:** A policy or RPC can expose data while every listed Playwright test passes because the client never tries the forbidden direct request. **Fix:** Before client work, write the complete migration and add authenticated/anon Data API tests proving:

   - Direct cross-user `profiles`, `sets`, and `group_members` reads fail.
   - Direct group/member/report writes fail.
   - Anonymous execution fails for every RPC.
   - Nonmembers cannot fetch boards.
   - Only the exact current 7/30-day ranges are accepted.
   - ACL catalog assertions and concurrent lifecycle tests pass.

9. **Serious · [§5 policies and §13.3 schema](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:704) · (a) definitely broken in this repository** — **Defect:** The new policies use plain `CREATE POLICY`, but the E2E global setup reapplies `schema.sql` every run. Existing policies in the schema are explicitly dropped first for this reason. **Failure:** The second E2E run fails immediately with `policy "groups_select" ... already exists`. **Fix:** Add `DROP POLICY IF EXISTS` before every policy, and drop/recreate functions when their return type or signature requires it.

10. **Serious · [§10.1 policy rollout](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:580) · (b) needs a product/legal decision before shipping** — **Defect:** Updating the copy does not present the new sharing terms to existing users. The current gate only checks an unversioned `policy_accepted` flag, so anyone who previously accepted passes without seeing the material change. **Failure:** An existing user joins and retroactively exposes their name and training breakdown under terms that still said there were no social features when they accepted them. **Fix:** Version policy acceptance and require acceptance of the Groups-era version before creating or joining a group. Store an auditable version/timestamp in a database table rather than relying solely on user-editable auth metadata.

11. **Serious · [§9.6 width budget](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:530) · (a) definitely broken arithmetic** — **Defect:** The stated columns already consume about 325 of 328 pixels, leaving three pixels for all gaps and padding. The budget omits the overflow-action control and own-row marker. **Failure:** A 360px device cannot fit rank, name, five numbers, spacing, and a tappable menu. A proper iOS menu target alone should normally be 44×44 points. [Apple also recommends avoiding horizontal scrolling and providing sufficiently sized controls.](https://developer.apple.com/design/tips/) **Fix:** Make total the primary right-hand value and put the four disciplines on a second line or expandable detail. Otherwise introduce horizontal scrolling now—not as a future fallback—and test long names, four-digit totals, and accessibility text sizes on real 360px devices.

## Minor findings

12. **Minor · [D18 and create flow](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:69) · (a) definitely broken rationale** — **Defect:** `leave_group` is idempotent in final state; retrying its silent no-op cannot duplicate harm. `create_group` is the ambiguous operation. **Failure:** Creation commits but the response is lost. Manual Retry gets `23505 “name taken”`, making the user think somebody else took it even though they created and joined it. **Fix:** Keep automatic retry disabled if desired, but pass a client-generated idempotency key or reconcile duplicate-name/network failures by refreshing and checking whether the caller is already a member of that group.

13. **Minor · [period memo](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:467) · (a) definitely stale** — **Defect:** A memo keyed only by `"7d" | "30d"` is a cache despite D15, and it ignores the actual date bounds. **Failure:** Load 7d before midnight, switch to 30d, cross midnight, then switch back: the header may show the new dates while rows come from yesterday’s window. It also misses sets logged while the page remains mounted. **Fix:** Remove the memo, or key it by `{group,start,end}` and invalidate on app resume, midnight, and relevant writes.

14. **Minor · [name normalization and error table](/C:/dev/iSkiLog/docs/superpowers/specs/2026-08-31-groups-design.md:110) · (b) verify against the eventual bodies** — **Defect:** The index itself does not collapse internal whitespace; it only works because the unwritten RPC promises to store canonical names. JavaScript and PostgreSQL also differ on Unicode whitespace and character counting. Explicit `NULL` inputs will commonly become `23502`, not the documented `22023`, unless checked deliberately. **Failure:** An admin/import path can insert both `"Ski Club"` and `"Ski  Club"`; emoji-heavy names can pass PostgreSQL’s code-point limit but fail a JavaScript UTF-16 limit; `create_group(NULL, '')` may surface an unmapped not-null violation. **Fix:** Centralize normalization in an immutable database function used by both a check/generated key and the unique index; test a shared Unicode corpus; explicitly reject nulls with the intended SQLSTATE.

The shown leaderboard aggregate itself is sound: the `LEFT JOIN`, filtered `count(s.id)`, grouping, and zero-set behavior work because `profiles.user_id` is unique and `event_type` is constrained. The unique index correctly arbitrates simultaneous creation once names are stored canonically. The trigger’s cascade recursion is also harmless in isolation; its concurrency behavior is the defect.
